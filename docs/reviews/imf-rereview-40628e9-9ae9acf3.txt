VERDICT
The implementation has improved materially. Answer-input leakage is gone from both SPO scripts. MQAR now randomizes bindings per sequence and prevents overlapping pairs. The scan now has a working CPU backward path. All 12 committed tests pass on CPU without a Triton stub, and a tiny double-precision numerical gradcheck also passes.

It is still a research prototype, not a validated production memory layer. The new SPO task does not define a learnable relation graph, MQAR changes its embedding codebook between train and evaluation, and the directionality test does not compare a baseline or test held-out associations. Several old headline claims and tables remain despite changes to the benchmark designs. Packaging and lower-precision fallback have reproducible failures.

These are implementation, experiment and documentation findings. They do not refute the symmetric/skew-symmetric decomposition or the owner's wider mathematics. Preserve the intended mathematics; settle the design questions explicitly rather than silently changing it.

NUMBERED FINDINGS AND ACCEPTANCE CONDITIONS

1. HIGH, BENCHMARK VALIDITY: SPO labels are random relative to the relations, not graph traversal. [READ + DERIVED + RAN sampling replay]
Locations:
  benchmark_spo_multihop.py:72-103, especially 83-88 and 95-98.
  stress_spo_multihop.py:45-66, especially 49-55 and 59-62.
The intermediate and tail entities are chosen by random offsets. Relation IDs are sampled independently after those entities. No relation transition function, fact store, graph edges or traversable memory is supplied to either model. The query contains only the starting entity and a sum of relation embeddings. Removing the answer leak was necessary, but it leaves the randomly chosen target unknowable from that query.

The relation sum also loses order: r1+r2 equals r2+r1. That cannot represent general ordered path composition. In the stress script, the same problem affects all three relations. Neither issue says that higher-arity binding is useless.

Pure-Python replay of the two-hop generator with its committed seed and train/test sizes produces two conflicting observable queries across the combined samples. Examples, using subject and sorted relation IDs: (4,7,11) has targets 12 and 14; (113,1,11) has targets 123 and 127. There were zero identical full train/test chains in this replay, so do not claim literal chain overlap was observed. Independent sampling does not, however, enforce disjointness as the docstring implies.

Even without sample collisions, the population target depends on independent random offsets, not the relations. For the two-hop generator, the most likely offset sum has probability 10/100. Perfect held-out retrieval is not available from the stated inputs.

Acceptance: define a fixed relation-labeled graph or transition rule; preserve relation order where order matters; provide the required facts/memory or enough training coverage of its rule. Deduplicate held-out queries deliberately and verify that each observable query has a defined target. Include a trivial subject-only baseline. Do not simply enlarge or train longer on the current random-label task.

2. HIGH, BENCHMARK VALIDITY: MQAR train/test use different random token codebooks. [READ + RAN codebook replay]
Locations: benchmark_mqar.py:51-56, 89-91, 124-154.
Each call constructs a new nn.Embedding, initializes it, then discards it after returning detached embeddings. Training calls the generator with seed 42; evaluation calls it with seed 1337. Thus token ID 200, for example, is represented by unrelated vectors in the two sets, but the classifier head still predicts fixed vocabulary IDs. The model receives no stable value-vector-to-ID decoder for the new test codebook.

This is not the same issue as the old static key/value map. That map is now correctly randomized per sequence, and key/value pair placements are now disjoint. Keep those fixes.

The function header promises multi-seed execution, but the actual runner has one fixed training batch, one test batch of 64 queries, no seed loop and no mean/std. Lines 148-154 repeatedly train on x_train rather than fresh batches. No new training result was run or inferred here.

Acceptance: create one persistent vocabulary embedding outside the batch generator, or return token IDs and keep the embedding inside the trained model. Use the same vocabulary encoding for train/test while randomizing per-sequence pairings. Generate fresh batches during training, separate evaluation randomness, and report multiple seeds with enough held-out queries. Add a context-free control that must fail on the sequence-specific mapping. If changing codebooks is intentional, use a compatible retrieval decoder and state that different task explicitly.

3. HIGH, BENCHMARK VALIDITY: polytope comparison remains a training-fit comparison. [READ]
Locations: benchmark_polytopes.py:78-86, 101-138.
One batch is generated before the preset loop. Each model fits that same batch for 100 steps; the displayed accuracy uses query_logits from the final training forward, before the final optimizer update. There is no held-out batch or seed loop. This cannot select a geometry for generalization or validate noise immunity.

Acceptance: adopt the corrected stable-codebook generator from item 2, fresh train batches, a shared held-out set for every preset, matched training budgets, controlled initialization where practical, multiple seeds and mean/std. Recompute final training metrics after the update if reported. Keep training fit clearly separate from retrieval generalization.

4. HIGH, BENCHMARK VALIDITY: new directionality test is memorization of A-to-B labels, not a SAVG effect test. [READ + RAN causal perturbation]
Locations: test_savg_directionality.py:45-91; test_savg_harness.py:63-82.
Only the SAVG wrapper is instantiated. The baseline named in the file's description is never trained or evaluated. The same 16 pairs are used for training and forward evaluation. Reverse leakage is mean cosine with A, not a candidate retrieval accuracy or a defined rejection/Nil decision.

B is placed at position 1, but predictions are read from position 0. TensorSAT's default hybrid layer is causal, and the added A_state is a prefix cumsum. Therefore position 0 cannot use the B at position 1. It can still learn the fixed mapping from each A vector to its B label across the 50 training steps, so this is not an impossible training task. It is not evidence of reading the association from context.

A tiny untrained wrapper check changed all tokens after position 0 and found maximum change at output position 0 equal to 0.0. No directionality training was run.

Acceptance: specify whether the goal is learned fixed associations or in-context directed memory. For the latter, put the query after a fact context and vary associations across examples. Train/evaluate a matched baseline from the same base weights and budget, use held-out task instances, and define forward accuracy, reverse false-positive rate and rejection threshold separately. Remove the implication that a low cosine alone proves rejection or a Reversal Curse solution.

7. MEDIUM, MATH / READOUT QUESTION: probe convention and cancellation claims remain unresolved. [DERIVED]
Locations: README.md:101-109; papers/01:66-82; triton_savg_kernel.py:59-66, 86-95, 160.
For A=(uv^T-vu^T)/2 acting on columns:
  A u = [u(v.u)-v||u||^2]/2
  A v = [u||v||^2-v(u.v)]/2.
The proportionalities to -v and +u require orthogonality or appropriate degenerate cases. The README includes the full formulas but still appends unconditional proportionality signs and unconditional reverse cancellation.

S+A=uv^T and S-A=vu^T. With equal decays and gates, neither split adds information to the corresponding outer product. The code reads S+A, whereas the README's verbal forward convention describes u->v and S-A. With unequal decays (the code uses 0.999 and 0.990), separate sectors can implement different dynamics. That is a legitimate design choice to evaluate, not an algebra defect.

Paper 01's conditional scalar score difference, 2*lambda*S_A, follows from symmetry/skew-symmetry. It is not a guarantee that all reverse scores are negative. For a single pair, S_A=(||u||^2||v||^2-(u.v)^2)/2 and S_S=(||u||^2||v||^2+(u.v)^2)/2. Negative reverse score requires lambda*S_A>S_S. In particular lambda=1 only gives exact zero for orthogonal nonzero probes; general probes give suppression rather than cancellation. The code's vector readout is not by itself a specified scalar rejection rule.

Acceptance: decide and document key/value roles, S+A versus S-A convention, probe assumptions, sector decays and rejection/readout. Test against an ordinary directional outer-product baseline. Keep the conditional theorem; remove unconditional operational conclusions that do not follow from it.

8. MEDIUM, PERFORMANCE / TEST GATE: backward works on CPU, but is a recomputation fallback and no timer exists. [READ + RAN CPU]
Locations: triton_savg_kernel.py:100-139, 164-200; tests/test_imf_components.py:58-73.
The custom autograd Function is a real improvement. First-order gradients flow through every layer parameter and the input. A tiny numerical gradcheck passes. This closes the old no-backward defect for the tested path.

Backward rebuilds the entire PyTorch recurrence graph at lines 132-138. It is not a fused backward kernel and does not inherit the forward kernel's constant recurrent-state memory profile. It can retain O(B*T*D^2) intermediates during recomputation. That tradeoff is acceptable if documented and measured. No large memory run was attempted.

run_timing_and_verification imports time but never measures elapsed time. It verifies output equivalence only when Triton/CUDA are available, and checks gradient presence, not gradient equivalence. One GPU program per batch element still loops over the whole sequence, with two BLOCK_D-square states. Performance and resource use require measurement, not assumptions from the word fused.

Acceptance: retain CPU fallback tests; add GPU forward and gradient comparisons against a dtype-consistent reference across sequence lengths, non-power-of-two D, strides and supported dtypes. Measure warmed-up, synchronized forward and forward+backward separately, including peak memory. Use tolerances justified for dtype and sequence length. Do not report 0.74 ms or production readiness from the CPU tests.

10. MEDIUM, GEOMETRY / GATE DESIGN QUESTIONS: bounded coordinates are not constrained regular geometry or positive modulation. [READ + RAN small checks]
Locations: polytope_connector.py:65-86, 98-129; README.md:114-138; papers/02:28-51.
Simplex anchors and orthoplex axes are learned Gaussian parameters, with no equal-distance or orthonormality constraint. Exact antipodal logits are implemented and should be credited; regular orthoplex geometry is not enforced. 'dimension' controls anchor count/projection count, not a restriction of the whole embedding space to that dimension.

The README defines a token-pair grid w(x)w(y)^T; the code uses a learned quadratic scalar w(x)^T G w(x). Resolve which object is intended. Softmax weights are normalized coordinates in a probability simplex, but do not establish exact barycentric reconstruction of arbitrary x.

No constraint ensures 1+w^T G w>0. The committed positivity unit test checks one random initialization only. A tiny deliberate allowed parameter setting, every entry of G=-2, yields modulation -1.0 at x=0. This shows the missing guarantee, not that ordinary initialization was observed failing. If positivity is required by the paper, constrain it or state the relevant assumption. The Gaussian initialization has no absolute positivity guarantee either.

Hypercube_factorized computes D tanh coordinates and a D-by-D quadratic form. It does not explicitly implement an XOR-coset construction, and its get_coordinates return shape is D rather than the num_vertices=2^D shape promised by the generic docstring. Tiny hypercube forward/backward passes, but no committed test covers it.

Acceptance: decide whether these are learned landmarks or constrained regular polytopes; describe or test the chosen contract. Specify scalar versus pairwise grid and positivity requirements. Clarify the factorized hypercube interface and avoid attributing a specific discrete factorization not implemented in the module. Do not change mathematical intent by guesswork.

12. MEDIUM, CODE DEFECT: half/bfloat16 reference path fails with a dtype mismatch. [RAN]

Float32 and float64 tiny direct-reference calls succeed. GPU behavior was not run. Because GPU backward recomputes this same reference, manually lower-precision CUDA training also needs explicit testing; do not claim AMP/CUDA autocast outcomes from this CPU test.

Acceptance: define supported input/state/accumulation/output dtypes, cast the read and write consistently, and test both fallback and backward under each supported mode. If only float32 is supported, reject other dtypes clearly and document that limit.
