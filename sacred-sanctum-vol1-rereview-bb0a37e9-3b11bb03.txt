R1 (A)  0.28 us is still claimed, and cannot be right. 
   Book line 4096-4097 now says in one paragraph: ncu bound "below 0.28 us (280 ns)" and, two lines later, ">= 2,048 cycles (~0.82 us)". It also remains in Table 5.2 (line 4037), line 4263, line 4314, line 5026, the Ch 8 ledger ("Silicon ALU Time (ncu) 280.1 ns, lie_kv_ncu_profile.txt").
   benchmark_results/lie_kv_ncu_profile.txt is internally impossible: Elapsed 280.12 ns at 2.54 GHz = ~711 cycles, but the same file says "Total Instructions Executed 2048" for one warp. One warp issues at most 1 instruction per cycle on its scheduler, so 2048 instructions need >= 2048 cycles = ~806 ns. It also says "Global Memory Load/Store Stalls 0" and "Registers Per Thread 32" while the kernel reads M and U from global and needs more than 32 registers. The file is plain text in a made-up layout, not an .ncu-rep export.
   FIX: delete 0.28 us everywhere, or replace it with a real `ncu --export` report (.ncu-rep) from the actual kernel and commit that. Safe statement: "launch-dominated 51.5 us measured; arithmetic lower bound ~0.8 us (2,048 instructions per warp)".
R2 (A)  SAVG "100% forward, 100% reverse" is a tautology (Ch 8 U9, ledger, benchmark_results/mqar_bidirectional_adapter.json).
   scripts/bench_mqar_bidirectional_adapter.py builds M_S = sum(v k^T + k v^T) and M_A = sum(v k^T - k v^T), then reads 0.5(M_S + M_A) = sum v k^T and 0.5(M_S - M_A) = sum k v^T. That is two plain linear-attention (outer-product) memories, one stored each way. There is no rotation U in it, no Lie dynamics, and the "reverse" readout is chosen by the script knowing it is a reverse query. The JSON has a hard-coded string "resolution_of_reversal_curse: CONFIRMED_VIA_DUAL_READOUT". Rerun: Forward 100%, Reverse 100% (reproduces), but it would be 100% for any outer-product memory at N=8, d=32.
   The reversal-curse claim needs a learned model that has to answer a reverse query without being told its direction. Say "dual-readout linear memory, a toy", or drop it from the ledger.
R3 (A)  "Block-diagonal speedup 32.0x (measured)" is neither measured nor 32x.
   benchmark_results/lie_block_diagonal_so4.json: flops_full 131,072, flops_block_diagonal 4,096, ratio 32. Pure FLOP arithmetic, no timing. The script comment says 3,072 but the code computes 4,096 (8*2*2*4^3 + 8*8*2*4*4), and neither matches the right count. Correct count for U M U^T with M 32x32 and U made of eight 4x4 blocks: each product is 8 blocks x (2*4*4*32) = 8,192 flops, so 16,384 for two products vs 131,072 dense = 8x (my run prints 8.0). The 8x also follows directly from "1/8 of U is non-zero". Theorem 8.1 item 4 (line ~5100) says 1,024 vs 32,768; dense one product is 65,536, and 8 x 2 x 4^3 ignores the 32 columns of M.
   FIX: say 8x arithmetic reduction (theoretical), move it from MEASURED to PROVED/COUNTED, and add a real kernel timing (csrc has a block-diagonal kernel, lines ~185-237) before calling it a speedup. Only U is block-diagonal: the innovation W = v k^T - k v^T (v,k in R^32) is not, so cross-block terms enter M anyway. Chapter 8 should say what the block-diagonal model drops.

4. WHAT CHAPTER 8 STILL NEEDS TO CONCLUDE AT d <= 4 / WHERE TO EXPAND
======================================================================
It now has: exact so(2), so(3), so(4) forms; the bridge; a ledger; ten unknowns. What it still lacks, in order of value:
 E1. The readout. A skew M built as U M U^T + W stores item i rotated by U^m (m = steps since it was written). Reading with the raw key only works for the newest item. Position-aware readout fixes that: query with U^m k_i, then un-rotate the output with U^{-m}. This is RoPE-style relative position, and it is the natural place where the Lie structure helps. 
     My run (same recurrence as scripts/bench_lie_capacity.py, d=32, random Cayley U, 100 trials each, unseeded rng seed 1):
        N=2: raw 0.805 -> position-aware 1.000
        N=4: 0.505 -> 1.000
        N=8: 0.271 -> 1.000
        N=16: 0.135 -> 0.997
        N=32: 0.064 -> 0.937
     This needs m, so a position index or a learned relative offset must be supplied. Next test: what happens at N=64 and 128 (the 496 degrees of freedom cap), and with token-conditioned A_t where m is unknown.
 E2. d<=4 completeness. Ch 8 section 1 states closed forms; add one runnable check for each (a script that verifies Rodrigues-Cayley, the quaternion Cayley, and the 4-d self-dual split numerically) and cite its output in the ledger.
 E3. A real DEC example: one triangulated torus or S^3 with Betti numbers b0..b3 computed by the C++ solver and printed in the book. Still missing; U5 only repeats the nilpotency test.
 E4. State what block-diagonal loses: the cross-block parts of W (so(32)/so(4)^8, the 496 - 48 = 448 parameters). That is the hand-off to Volume II, and it should be a sentence in Chapter 8.
 E5. Short "Failure modes" box: no capacity beyond ~N<=16 with fixed U and raw readout; bf16 drift needs renormalisation; kernel is static transport; no trained model uses the state yet.
 E6. A single "reproduce everything" command (one script that runs all scripts/bench_*.py and tests/ with fixed seeds and writes the ledger numbers), so every MEASURED row in Table 8.1 has a file and a command.
